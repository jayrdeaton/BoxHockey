# BoxHockey

Physics-driven tabletop box hockey against the CPU or a friend across the table (Expo/React Native, Skia-rendered). Store name BoxHockeyTastic. Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem - depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `@tastic/sprites` (the `./gravity` subpath only, for the gravity-well particle-swirl visual - see `src/components/GravityWellMarker.tsx`), `@tastic/core`, `@tastic/hud`, `@tastic/input`, `@tastic/physics`, `@tastic/profile`, `@tastic/split-screen`. The gravity well's *force* math (`applyGravityWells`, bounded quadratic falloff) stays in `@tastic/physics` - only the cosmetic particle-swirl rendering moved to `@tastic/sprites`; the two packages compose at this app's own call sites, neither depends on the other.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code - don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (24 suites, 352 tests)
npm run test:watch     # Jest --watchAll
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) - `verify` doesn't include a build step.

**Builds and OTA updates:** the `build` and `update` scripts are plain `eas build` and `eas update`, with profiles in `eas.json` (`development`, `preview`, `production`). Pass the profile through, e.g. `npm run build -- --profile preview` or `npm run update -- --branch production --environment production --message "..."`. Nothing in them runs `verify`, so run `npm run verify` first. An OTA update also bumps `otaVersion` in `src/constants/release.ts` (the version label players see), committed before publishing. They used to be `@rific/updater`'s `rific-updater-build`/`rific-updater-update` bins, which @rific/updater 0.7.0 removed; the package stays for its OTA update hook.

**`jest.config.ts` became `jest.config.cjs`, matching every non-Expo project in the fleet - no more `ts-node` gotchas.** This app (like every other Expo app) originally had `jest.config.ts` while every library/kit package used `.cjs` - a real divergence, not a justified one. `.ts` needed `import type {Config} from 'jest'` + a typed `const config: Config = ...` (a bare `export default createExpoJestConfig(...)` fails `tsc`'s declaration-emit check), plus a separate non-extending `tsconfig.jest.json` wired in via `TS_NODE_PROJECT=./tsconfig.jest.json` on `test`/`test:watch` (`ts-node`, Jest's `.ts`-config loader, can't resolve a tsconfig `extends` through a package's `exports` map at all). None of that exists for `.cjs` - plain `require()`, no transpilation, nothing to typecheck. Converting removed `tsconfig.jest.json`, the `TS_NODE_PROJECT` prefix on both scripts, and the `ts-node` devDependency entirely - see `@infinitetoken/jest-config`'s own README ("Why `.cjs`, not `.ts`") for the full history.

**`prettier.config.js` was deleted - `package.json` now has `"prettier": "@infinitetoken/eslint-config/prettier"` instead**, same as every library/kit package. The local file was a byte-for-byte duplicate of the shared package's own `prettier.cjs`; every Expo app had independently copy-pasted it rather than referencing the shared one.

Swirlio never had this file at all and works the same way - this file's presence elsewhere in the fleet is boilerplate carried over from `expo customize`, not a requirement.

**`@shopify/react-native-skia` needs an explicit `paths` redirect to its compiled `.d.ts`, or typecheck fails inside the package's own source.** Identical root cause and fix as Swirlio: no `exports` map, `customConditions: ["react-native"]` follows the raw `src/index.ts`, which pulls in an upstream unused-`React`-import that only fails once `noUnusedLocals` turns on. ## Bug fixes (2026-09-17)

**`Theme.tsx` marked its `'theme'` splash gate ready immediately instead of waiting for `AutoPaperProvider`'s own `onReady`.** A fleet-wide audit found this app's `Theme.tsx` calling `useSplashReady('theme', true)` unconditionally right after reading the Redux `theme` slice, reasoning (in its own now-removed comment) that `PersistGate` already resolving `settings` was enough - but `AutoPaperProvider` itself still renders `null` internally until it's actually computed a theme object from that settings value, a separate, later step. Marking the gate ready before that could let the splash screen lift while `AutoPaperProvider` was still rendering `null` underneath it. Fixed to match every sibling app's `Theme.tsx`: `const onReady = useCallback(() => markSplashReady('theme'), [])` passed to `<AutoPaperProvider onReady={onReady}>`. LightCycles had the identical bug and was fixed the same way in the same pass.

Face-to-face two-player achievement-unlock toasts were unreadable to the upside-down seat - this one genuinely is fixed. `showAchievementToast` is a single, screen-fixed `@rific/toaster` call with no rotation of its own, so in pass-and-play a player seated opposite (rotated 180° - see `isUpsideDown`) couldn't read a toast for their own unlock. Fixed in `src/app/game.tsx` by routing two-player unlocks into new per-seat `seatUnlocks` state (`Partial<Record<Player, AchievementDefinition[]>>`, declared in `GameScreen`) instead of firing the toast, rendered as a small badge list inside `MatchOverlays`' existing Game Over card - which already carries its own `cardRotationStyle` - rather than a screen-fixed overlay. Device-wide achievements have no per-seat owner, but both seats are human in this mode, so they're broadcast into both seats' `seatUnlocks` entries rather than dropped or arbitrarily attributed to one side. `vsCpu` (only one human seat) is unaffected and still calls `showAchievementToast` unconditionally. Mirrors a pattern LightCycles had already built for itself (its own `profileUnlockToast` state, same `Partial<Record<Player, AchievementDefinition[]>>` shape, same Game-Over-card rendering) under a different local name. (Superseded 2026-10-20: 2 Player unlocks are toasts turned to face each seat; see "Unlock toasts" at the end.)

**A live browser check of AirHockey's `/loadout` screen (this app's own migration work is byte-for-byte the same shape) turned up a real bug in `@rific/core`, upstream of this app's own `Theme.tsx`/`GameSettingsProvider`/`OrientationProvider`.** `createSettingsContext`'s `set()` called the consumer's `onChange` *inside* the `useState` updater passed to `setSettings` - a `useState` updater must be pure, since React can invoke it outside the originating `set()` call (e.g. replaying a queued update while resolving a later render of the very same Provider), and when that happened, `onChange` (which `Theme.tsx` wires straight to `dispatch(themeActions.initialize(...))`) fired synchronously mid-render of an unrelated component - a genuine "Cannot update a component while rendering a different component" React warning. This factory backs `@rific/auto-paper`'s `Theme`, `@rific/feedback-press`'s haptic/sound settings, and `@rific/scroll-view`'s settings context alike. The same audit found the identical shape independently duplicated, not through this factory, twice more inside `@tastic/core`: `createGameSettingsProvider`'s `setSettings` called `AsyncStorage.setItem` from inside its own updater, and `OrientationProvider`'s `set` called the consumer's `onLockChange` the same way - both used by this app. All three were fixed the same way: the side effect moved into a `useEffect` keyed on the settled state, skipping the mount-time run so the contract (onChange/persistence only fires for a real `set()` call, never for `initialValue`/`defaultSettings` seeding) is unchanged. Now on `@rific/core@0.1.2` and `@tastic/core@0.5.1` (both patch bumps, no API change) - this app's own `npm run verify` (259/259 tests) stayed green through the bump.

**Same pass also found and fixed a real gap in `@infinitetoken/jest-config`'s `knownSubpathMocks`:** it stubbed `@rific/feedback-press/audio`'s `useAudioPool` but not `useGatedAudioPool` - a real risk for this app specifically, since `hooks/useGameSound.ts` re-exports `useGatedAudioPool` directly, and any future test rendering a component that calls it would have hit real `expo-audio`/native audio APIs during a Jest run instead of the intended inert stub. Fixed by adding the same inert-hook stub for it. Now on `@infinitetoken/jest-config@0.3.1`.

**`@tastic/hud@0.9.0` closed the `PlayerSetupPanel` CPU-difficulty alignment gap this app's own earlier migration agent found blocked (no override prop existed at all for the panel's internal `LabeledDropdown`) - `loadout.tsx`'s `p2Panel` now wires the new `cpuDifficultyAlignOverride` prop via `useZoneClampedAlign(p2Host.openId === getCpuDifficultyPopoverId('p2'), LABELED_DROPDOWN_POPOVER_WIDTH, getLabeledDropdownContentHeight(AI_DIFFICULTY_OPTIONS.length))`.** Confirmed, from the actual render tree (not assumption), that this is a documented no-op for this app: `p2Panel`'s CPU seat only exists in `vsCpu` mode, which always renders through the plain stacked (non-`DualZoneLayout`) branch below - only `gameMode === 'twoPlayer'` gets a real `@tastic/split-screen` zone - so `useZoneBounds()` is null there and `useZoneClampedAlign` falls straight back to `useAutoAlign`'s own plain screen-edge placement, same conclusion LightCycles' own `lobby.tsx` already documented for its identical seat before this prop existed. Wired in anyway, for parity with every other zone-aware popover in the fleet and so it starts clamping for free if `vsCpu` is ever nested inside a zone later. `npm run verify` (259/259 tests) stayed green. (Superseded 2026-10-17: see "The seat button" below.)

## Fleet package extraction round 2 (2026-09-18)

## Settings and Lock Orientation (2026-10-07)

**Settings live in Redux**, like every other persisted value: `src/redux/settingsSlice.ts` (`DEFAULT_SETTINGS` plus `@rific/core`'s `createSettingsSlice('settings', { initializeMode: 'merge' })`), read and written only through `useSettings()` (`src/hooks/useSettings.ts`, returning `{ settings, setSettings(patch) }`). ## Background pause and stale seat profiles (2026-10-08)

- **Leaving the app mid-match pauses it until the player resumes.** `game.tsx` calls `@tastic/core`'s `useBackgroundPause(() => phase !== 'gameOver' && !settingsOpen && !confirmVisible)` and folds the latch into `paused = settingsOpen || confirmVisible || backgroundPaused`, so everything a dialog halts (physics loop, scored/coin-flip/face-off/triple-tap timers, CPU chains, Edge Guard) halts the same way. ## Triple Tap tip-off (2026-10-18)

Rebuilt to Jay's design: both players tap their own half `TRIPLE_TAP_TAPS` (3) times **in step** (a tap only counts while you aren't already ahead of the other player, `canTripleTap` in `useGameState.ts`; you can lead by one, then wait), then race to swipe. The swipe is judged exactly like a Flick shot (`resolveStrikeVelocity('flick', ...)`, so a stray extra tap never launches a dud). The first real swipe launches the puck off center at once (`TRIPLE_TAP_SWIPE`, swiper becomes `currentPlayer`, bookkeeping only). The other player's swipe within `TRIPLE_TAP_CLASH_WINDOW_MS` (250, first-pass, tune on a device) is added onto the moving puck with `combineAndClampVelocity` and knocks it off its line; later is too late. `TripleTapState` stays set (phase `simulating`) through that window so the trailing player's gesture and Board's latched ripple/streak survive the launch; `useTripleTap.ts`'s timer dispatches `TRIPLE_TAP_CLASH_END` to clear it.

- **Input:** a player's whole half (game.tsx's triple-tap views), live during the draw and, for the trailing player only, the clash window. The gestures key on those booleans, not `phase`, so the launch doesn't rebuild a drag in progress. `tripleTapKeys` remounts a zone's detector after EVERY release, counted or not (an ignored early tap changes no reducer state, and a still-mounted recognizer drops the next tap). Only a counted tap or a gate-passing swipe buzzes, so an ignored tap reads as "wait".
- **Visual:** no big circle any more (`tripleTapZoneCenter`/`Radius` and `TRIPLE_TAP_ZONE_RADIUS_RATIO` are gone). Each player's two rink face-off circles fill a little more per counted tap, ripple on each tap and breathe once all taps are in, with 3 tap pips between them; each swipe draws a streak from center.
- **CPU:** taps whenever a tap would count, after a reaction delay (so it follows the human in step), then swipes after reaction plus drag time; its swipe timer stays armed through the clash window, so a fast human can still get clashed.
- Tested in `tripleTap.test.ts` (lockstep, tap cap, swipe gating, launch, clash in and out of the window, CLASH_END, CPU swipes passing the gate, turn-alternation fuzz). **Not checked live on a device yet**, and the mode is touch-only (hidden on web), so a simulator or phone is the only way to feel it.

## Stick control (2026-10-18)

A fourth control scheme, `'stick'`, next to Flick (Flick stays the default; Jay wants to try Stick on a device first). The finger is the stick blade, and the shot is the contact, not a release: `src/utils/stick.ts` holds the pure physics, and the reducer runs it.

- **The hit** (`resolveStickContact`): the blade is a circle (`STICK_BLADE_RADIUS_RATIO` of the puck's radius, generous because the finger covers the puck), swept against the puck in the puck's own frame, so a moving puck and a moving blade both count. Along the contact normal (blade through the puck's center) the puck leaves at `(1 + STICK_RESTITUTION)` times the blade's approach speed, plus `STICK_CARRY` of the blade's sideways motion, clamped to `MAX_SPEED`. A square hit is a full shot, a glancing one a soft sideways one. An approach under `STICK_MIN_HIT_SPEED` is no hit. Finger points/sec convert to puck units with `STICK_VELOCITY_SCALE` (1/60: a puck unit is points per 60Hz step). All of these are first-pass values to tune by feel.
- **Where it runs:** `useGameState.ts`'s `stickSwing`, from `AIM_UPDATE` (which now carries `board`; `aimUpdate` passes `boardRef.current`) for a normal turn or a CPU intercept, and from `PHYSICS_STEP` for a human intercept (the finger arrives through `interceptTouch`), so a blade held still in a sliding puck's path deflects it. A hit goes straight to `'simulating'` like a flick release; an intercept hit also hands `currentPlayer` to the interceptor. The blade has to be clear of the puck at the start of a step to hit (`AimIndicator.stickClear` records "clear right now" for Board), so touching down on the puck does nothing until the finger leaves.
- **Missing is free:** releasing without a hit (`STRIKE`) is a whiff, back to `'idle'` on the same turn, with a fresh `puck` object so `useAIOpponent`'s turn effect (keyed on it) re-plans for a CPU that whiffed. A missed intercept just drops the `interceptAim`.
- **Walls and corners:** `clampBladeToBoard` keeps the blade (both ends of every step, touch-down included) inside the walls stepPhysics bounces off, rounded rink corners included. A puck against a wall or in a corner can't be hit from the wall side, only dug out from the open side; a hit into the walls bounces out with normal wall physics. Goal mouths, the center divider and gauntlet blocks are not walls for the blade (a real stick reaches over them).
- **CPU:** `planStickSwing` turns `planAIShot`'s direction and power into a swing (touch down behind the puck, swing through it at `bladeSpeedForShot`); if the contact point is off the ice (a cornered puck planned into the corner) it swings in the nearest reachable direction instead. `useAIOpponent.ts`'s `scheduleStickSwing` plays it through `tryAimStart`/`aimUpdate`/`shoot` in 16ms steps, placed relative to the live puck so an intercept tracks a moving one.
- **Board:** no pulled-back stick, chevrons, front arrow or phantom puck for Stick. It draws the blade where it is (every preview tier) and, above `'off'`, a faint line from the puck straight away from the blade (where a square hit would go) while the blade is clear. `game.tsx` buzzes on the hit itself (`prevStickRef`) and skips the cancel-zone tick.
- **Fixed in passing:** `tryAimStart` clears `interceptTouchRef`, which was never reset, so a new intercept's first physics step folded in the previous drag's last finger position (for a Stick interceptor, a bogus swing across the board).
- **Copy:** loadout option "Stick: Swing into the puck to hit it" (`hockey-sticks` icon, second in the picker); guide card "Swing your finger into the puck. It flies away from your finger. Faster swings hit harder." (the mouse on desktop), and the mixed-scheme sentence drops "Start anywhere" when a seat plays Stick.
- **Tested:** `stick.test.ts` (square, glancing, capped and non-hits; a held blade deflecting a moving puck; wall and rounded-corner clamping; reducer hit, whiff, land-on-the-puck, cornered puck unreachable from the wall side but dug out from the open side, a Stick intercept; the CPU planner's reachable direction and its swing landing through the reducer), and `guideSteps.test.tsx` now covers Stick in every copy rule. **Checked live on web (2026-10-18)** through the real gesture handler with timed pointer events: a miss stays on the same turn, a square swing sends the puck straight away at full speed, and a glancing one sends it off to the side, softer. **Not checked on a device**, where the feel (blade size, power, carry) has to be tuned, and the CPU's Stick play and Stick intercepts haven't been watched live.

## Rink and Gravity physics (2026-10-18)

Found by replaying the real physics headlessly (an esbuild bundle of `stepPhysics`, `computeBoardLayout`, `planAIShot` and the face-off knock with a `react-native` Platform stub, the way `store/seed/generate.mjs` does it) on the iPhone 17 Pro Max layout (440x956, insets 62/34). Both fixes are in `src/utils/physics.ts` and pinned by `src/__tests__/gravityRink.test.ts`.

- **A puck behind a goal line beside the net could score (Rink only).** The pocket behind each line is open ice, so a puck resting there outside the posts is normal (face-off knocks end there often). But one sliding along just behind the line could rise into "not fully behind" by a fraction of a pixel with its center still outside the posts, carry its center into the goal's x-range on the next substep, and get shoved back past the line by the post (posts only skip a puck that is FULLY behind), which the score check read as a fresh crossing. About 2% of goals on Gravity or Classic with Rink were these, almost all the Hard CPU's: `planAIShot` replays `stepPhysics`, so it found and took them from exactly the reported spot. Fix: the score checks (in `stepPhysicsOnce` and `computeTrajectory`) use `cameFromBehindTop`/`cameFromBehindBottom`, which also count a puck whose CENTER was already past the line outside the goal's x-range at the start of the step. The posts and the one-way door still use `wasBehindTop`/`wasBehindBottom`. Checked: every goal this removes was one from beside the net, no goal through the mouth is lost, and Rink off is unchanged.
- **Gravity's center attractor could hold the puck forever at a low frame rate.** Its center sits on classic's divider; at a steady dt of about 1.25 or more (40 fps or slower) its pull on a puck touching the divider, bounced back at `WALL_RESTITUTION`, kept the puck above `STOP_THRESHOLD` every frame, so it looked still while 'simulating' never ended. Fix: `stepPhysics` splits any frame into steps of at most dt 1 (the wells, friction and `STOP_THRESHOLD` are tuned per 60 Hz frame). dt 1 and below play exactly as before.
- **Not the cause:** the corner repellers (`activeAtRest`) never kept a puck moving at that spot on any dt from 0.5 to 2.5; their reach ends before the back wall and the side wall. The physics alone doesn't explain the 30+ second wait itself (no never-ending state was found in the bottom-right pocket); the goal from behind the net does explain "came to rest there, then the next face-off". **Not checked on a device or simulator yet.**

Handing it the module is what turns the feature on: without it `useKeepAwake` does nothing and hud hides the row. `useKeepAwake` drops both expo-keep-awake rejections (web refuses a wake lock in a frame without the Permissions-Policy, and rejects a release when none is held). The old `settings.keepAwake` field, its default and the hand-rolled `/game` effect are gone, and the value saved under it was abandoned (no migration: the games aren't on the App Store), so a player who had turned it off starts back on.
- The row is `@tastic/hud`'s (0.23.0+): `BaseSettingsDialog` reads core's setting itself, with no props, and shows the row (caption "Stop auto-lock mid-match") only when `useExpoKeepAwake()` returns a module and the device is touch-first (native and touch-first browsers), like Lock Orientation. Needs `@rific/core` 0.4.0+.
- `expo-keep-awake` was already installed as a dependency of `expo`, so it is already in existing native builds; it's a direct dependency (`~58.0.3`). No new native build needed.
- Same in AirHockey, BoxHockey, LightCycles, Pong and Snake (the four with the shared `Providers.tsx` have the same `KeepAwakeBridge` byte for byte; Snake's sits next to its ScrollViewBridge), and in ArcheryDuel, Hangman, HexFleet and Solitaire. Checked on web (2026-10-15, the per-game version before core): `/game` took the wake lock on mount and released it on exit, took none with the setting off, and the toggle took or released it mid-match; the row showed on a touch device and hid on desktop. Not checked on a device yet: a release build staying lit through a long rally.

## Status bar: per-screen options (2026-10-15)

The OS status bar is set through react-native-screens' screen options, never a `StatusBar` component. `_layout.tsx`'s `AppStack` (identical across AirHockey, BoxHockey, LightCycles and Pong) spreads `@tastic/core`'s `useRotationAwareStatusBar()` (0.14.0+) into the root Stack's `screenOptions`, which hides the bar while the content is rotated off portrait (no `locked` argument: `OrientationBridge` freezes the reading it follows), and /game hides it for the whole round through its own `Stack.Screen` options (`GAME_OPTIONS`, `{ statusBarHidden: true }`), set in the layout so they apply as the screen is pushed rather than one effect later. No style is passed: react-native-screens' default (`auto`, following the system appearance) is what expo-status-bar's `auto` gave before.

Why: an app linked against the iOS 27 SDK (Xcode 27) can't set the status bar through `UIApplication` any more (UIKit's `UIApplication.h`: setting it "does nothing if ... linked against SDK versions 27.0 or later"), and that is all React Native's `StatusBar`, and so expo-status-bar, does on iOS. `@tastic/core`'s config plugin now sets `UIViewControllerBasedStatusBarAppearance: true`, which react-native-screens needs, and under which every mounted `StatusBar` logs an `RCTLogError` (a red box in dev). So nothing may mount one: `<RotationAwareStatusBar />` (removed from core) and /game's `<StatusBar hidden />` are gone, `Theme.tsx` passes auto-paper's Provider `statusBar={false}` (0.13.2+, which also covers `Appbar.Header`), and expo-status-bar is no longer a dependency or an app.json plugin (its plugin did nothing without options). Pinned by `src/__tests__/statusBar.test.tsx` (no source file imports expo-status-bar or React Native's `StatusBar`; Theme turns auto-paper's off).

- **The hide only shows in a Release build.** In a dev-client (development) build, expo-dev-launcher inserts its own view controller above react-native-screens' stack, so the screens' status bar options never reach UIKit and the bar never hides there, rotated or on /game (see @tastic/core's CLAUDE.md, "Status bar: per-screen options"). Check it in a preview/production build or a local Release build.
- **It needs a new native build.** `UIViewControllerBasedStatusBarAppearance` only reaches Info.plist at prebuild, and the app.json plugin list changed too, so the fingerprint runtime version moves on: an OTA update from here on won't reach an older binary.
- Android gets the same options from react-native-screens (no Info.plist key there). Not checked on a device on either platform.

## Gesture callbacks leaked the game screen (2026-10-18)

react-native-worklets keeps a native strong reference (a Hermes GC root) to every `runOnJS`/`scheduleOnRN` target for as long as the calling worklet's serialized copy lives, and the copy is cached while the component holds its gesture. `game.tsx`'s gestures called the screen's own `stable*` callbacks that way, so the screen was never collected. They now call `scheduleOnRN(callWorkletCallback, key, ...args)`, with each key from `useWorkletCallback(stableX)` (`@rific/core` 0.5.0), so the gestures hold only a string key and the latest callback is looked up at call time. The gesture deps are the keys (stable for the component's life), so the tripleTapKeys detector remount per press is unchanged. Never hand `runOnJS`/`scheduleOnRN` a callback the same component also reaches its worklet from. The gestures use `scheduleOnRN` from `react-native-worklets` (2026-10-18), since `runOnJS` is deprecated in Reanimated 4; the key scheme is unchanged. JS only, so it can ship in an OTA. Not verified on a device.
