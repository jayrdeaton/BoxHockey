# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

# BoxHockey

A digital BoxHockey game (Expo/React Native, Skia-rendered). Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem — depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/focus-chain`, `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `@tastic/sprites` (the `./gravity` subpath only, for the gravity-well particle-swirl visual — see `src/components/GravityWellMarker.tsx`), `@tastic/core`, `@tastic/hud`, `@tastic/input`, `@tastic/physics`, `@tastic/profile`, `@tastic/split-screen`. The gravity well's *force* math (`applyGravityWells`, bounded quadratic falloff) stays in `@tastic/physics` — only the cosmetic particle-swirl rendering moved to `@tastic/sprites`; the two packages compose at this app's own call sites, neither depends on the other.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code — don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (13 suites, 286 tests)
npm run test:watch     # Jest --watchAll
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) — `verify` doesn't include a build step.

`build`/`update` delegate to `@rific/updater`'s own `rific-updater-build`/`rific-updater-update` CLI bins, which run this app's `npm run verify` internally as their first step — there is no per-profile `build:development`/`update:production`-style script in this app's `package.json` and no `npm run verify && ` prefix anywhere; that older per-script-prefix pattern predates these bins and no longer applies. See `@rific/updater`'s own README ("Verify-gating lives in the CLI, not in `package.json`") for the full mechanism.

## Tooling

Onboarded onto the shared `@infinitetoken` config packages (`eslint-config`, `jest-config`, `tsconfig`) — previously hand-rolled its own `eslint-config-expo`-based config, `jest-expo`-preset-direct config, and `expo/tsconfig.base`-extending tsconfig (the same pattern documented in [Swirlio](../Swirlio/.claude/CLAUDE.md)'s and [LightCycles](../LightCycles/.claude/CLAUDE.md)'s CLAUDE.md, which this migration followed).

`npx expo install --fix` + `npm update` were run as part of this pass too (`expo install --fix` genuinely found something here — `expo`/`expo-updates` were a patch behind) — confirmed clean afterward: `npx expo install --check` reports up to date, `npm outdated` shows `Current === Wanted` for every dependency (remaining `Latest` values are all major bumps outside declared ranges, a deliberate-upgrade decision, not routine maintenance).

- `eslint.config.cjs` — `@infinitetoken/eslint-config/expo`, no local override (see below)
- `tsconfig.json` — `extends: "@infinitetoken/tsconfig/expo"`, keeps only the path-valued local bits (`paths`, `include`), plus two narrow `@shopify/react-native-skia` redirects (see below)
- `jest.config.cjs` — `@infinitetoken/jest-config/expo`, no options at all — `jest.setup.cjs` and `roots` are both auto-detected/defaulted (see below)

**`jest.config.ts` became `jest.config.cjs`, matching every non-Expo project in the fleet — no more `ts-node` gotchas.** This app (like every other Expo app) originally had `jest.config.ts` while every library/kit package used `.cjs` — a real divergence, not a justified one. `.ts` needed `import type {Config} from 'jest'` + a typed `const config: Config = ...` (a bare `export default createExpoJestConfig(...)` fails `tsc`'s declaration-emit check), plus a separate non-extending `tsconfig.jest.json` wired in via `TS_NODE_PROJECT=./tsconfig.jest.json` on `test`/`test:watch` (`ts-node`, Jest's `.ts`-config loader, can't resolve a tsconfig `extends` through a package's `exports` map at all). None of that exists for `.cjs` — plain `require()`, no transpilation, nothing to typecheck. Converting removed `tsconfig.jest.json`, the `TS_NODE_PROJECT` prefix on both scripts, and the `ts-node` devDependency entirely — see `@infinitetoken/jest-config`'s own README ("Why `.cjs`, not `.ts`") for the full history.

**`prettier.config.js` was deleted — `package.json` now has `"prettier": "@infinitetoken/eslint-config/prettier"` instead**, same as every library/kit package. The local file was a byte-for-byte duplicate of the shared package's own `prettier.cjs`; every Expo app had independently copy-pasted it rather than referencing the shared one.

**`metro.config.js` was deleted — it was unmodified `getDefaultConfig(__dirname)` boilerplate doing nothing.** Confirmed by removing it and running `npx expo export -p web`: builds cleanly, `canvaskit.wasm` still lands in `dist/` (copied into `public/` by the `setup-skia-web` postinstall script and served as a static file, fetched at runtime by `canvaskit-wasm`'s own init code — never `require()`d through Metro's bundler, so `resolver.assetExts` is irrelevant to it regardless). Swirlio never had this file at all and works the same way — this file's presence elsewhere in the fleet is boilerplate carried over from `expo customize`, not a requirement.

**`@shopify/react-native-skia` needs an explicit `paths` redirect to its compiled `.d.ts`, or typecheck fails inside the package's own source.** Identical root cause and fix as Swirlio: no `exports` map, `customConditions: ["react-native"]` follows the raw `src/index.ts`, which pulls in an upstream unused-`React`-import that only fails once `noUnusedLocals` turns on. Two `paths` entries redirect the bare specifier and the `@shopify/react-native-skia/src/web` deep path (`src/utils/loadSkiaWeb.web.ts` imports it directly to lazy-load the CanvasKit WASM runtime) to their compiled counterparts.

**Native/Expo module mocks moved from inline `jest.mock()` calls in `jest.setup.cjs` into individual `src/__mocks__/*.ts` files** — `react-native-reanimated`, `react-native-worklets`, `@expo/vector-icons` (+ its `createIconSet` deep import), `expo-splash-screen`, `react-native-gesture-handler`, `react-native-safe-area-context`, `expo-router`. This is a fleet-wide convention change, not BoxHockey-specific — see `@infinitetoken/jest-config`'s own CLAUDE.md for the full reasoning (manual `__mocks__/` mocking works fine under `jest-expo`, contrary to what that package's docs used to claim; `roots: ['<rootDir>/src']` is now a default there specifically so `src/__mocks__/` — not root `__mocks__/` — is where Jest picks them up, next to `src/__tests__/`). `jest.setup.cjs` now holds only genuine setup-file content (the `IS_REACT_ACT_ENVIRONMENT` flag, `unhandledRejection`/`uncaughtException` handlers, the RAF/cancelAnimationFrame polyfills, and the no-factory `NativeAnimatedHelper` automock) and is auto-detected by `@infinitetoken/jest-config/expo` — no `setupFilesAfterEnv` option needed at all. Also renamed from `.ts` to `.cjs` — a later, separate cleanup: auto-detection genuinely supports either (a `.ts` setup file goes through Jest's own test transform same as any other `setupFilesAfterEnv` entry, unlike `jest.config.cjs` itself, which Jest loads directly before any transform exists), but once its content shrank to thin boilerplate with the mock factories gone, there was no remaining reason for this one hand-authored config file to use a different extension than every other one in the app — see `@infinitetoken/jest-config`'s README, "Why `.cjs`, not `.ts`." With the mock factories' `any` usage gone, `jest.setup.cjs` no longer needs its own `no-explicit-any` eslint override — `eslint.config.cjs` is back to the plain one-liner, same as Crumby. The one remaining `any` in `jest.setup.cjs` (bridging `requestAnimationFrame`'s polyfilled `NodeJS.Timeout` return type into `cancelAnimationFrame`'s DOM-lib `number` signature) is a single targeted `eslint-disable-next-line`, not a file-wide exemption.

## Bug fixes (2026-09-17)

**`Theme.tsx` marked its `'theme'` splash gate ready immediately instead of waiting for `AutoPaperProvider`'s own `onReady`.** A fleet-wide audit found this app's `Theme.tsx` calling `useSplashReady('theme', true)` unconditionally right after reading the Redux `theme` slice, reasoning (in its own now-removed comment) that `PersistGate` already resolving `settings` was enough — but `AutoPaperProvider` itself still renders `null` internally until it's actually computed a theme object from that settings value, a separate, later step. Marking the gate ready before that could let the splash screen lift while `AutoPaperProvider` was still rendering `null` underneath it. Fixed to match every sibling app's `Theme.tsx`: `const onReady = useCallback(() => markSplashReady('theme'), [])` passed to `<AutoPaperProvider onReady={onReady}>`. LightCycles had the identical bug and was fixed the same way in the same pass.

Face-to-face two-player achievement-unlock toasts were unreadable to the upside-down seat — this one genuinely is fixed. `showAchievementToast` is a single, screen-fixed `@rific/toaster` call with no rotation of its own, so in pass-and-play a player seated opposite (rotated 180° — see `isUpsideDown`) couldn't read a toast for their own unlock. Fixed in `src/app/game.tsx` by routing two-player unlocks into new per-seat `seatUnlocks` state (`Partial<Record<Player, AchievementDefinition[]>>`, declared in `GameScreen`) instead of firing the toast, rendered as a small badge list inside `MatchOverlays`' existing Game Over card — which already carries its own `cardRotationStyle` — rather than a screen-fixed overlay. Device-wide achievements have no per-seat owner, but both seats are human in this mode, so they're broadcast into both seats' `seatUnlocks` entries rather than dropped or arbitrarily attributed to one side. `vsCpu` (only one human seat) is unaffected and still calls `showAchievementToast` unconditionally. Mirrors a pattern LightCycles had already built for itself (its own `profileUnlockToast` state, same `Partial<Record<Player, AchievementDefinition[]>>` shape, same Game-Over-card rendering) under a different local name.

**A live browser check of AirHockey's `/loadout` screen (this app's own migration work is byte-for-byte the same shape) turned up a real bug in `@rific/core`, upstream of this app's own `Theme.tsx`/`GameSettingsProvider`/`OrientationProvider`.** `createSettingsContext`'s `set()` called the consumer's `onChange` *inside* the `useState` updater passed to `setSettings` — a `useState` updater must be pure, since React can invoke it outside the originating `set()` call (e.g. replaying a queued update while resolving a later render of the very same Provider), and when that happened, `onChange` (which `Theme.tsx` wires straight to `dispatch(themeActions.initialize(...))`) fired synchronously mid-render of an unrelated component — a genuine "Cannot update a component while rendering a different component" React warning. This factory backs `@rific/auto-paper`'s `Theme`, `@rific/feedback-press`'s haptic/sound settings, and `@rific/scroll-view`'s settings context alike. The same audit found the identical shape independently duplicated, not through this factory, twice more inside `@tastic/core`: `createGameSettingsProvider`'s `setSettings` called `AsyncStorage.setItem` from inside its own updater, and `OrientationProvider`'s `set` called the consumer's `onLockChange` the same way — both used by this app. All three were fixed the same way: the side effect moved into a `useEffect` keyed on the settled state, skipping the mount-time run so the contract (onChange/persistence only fires for a real `set()` call, never for `initialValue`/`defaultSettings` seeding) is unchanged. Now on `@rific/core@0.1.2` and `@tastic/core@0.5.1` (both patch bumps, no API change) — this app's own `npm run verify` (259/259 tests) stayed green through the bump.

**Same pass also found and fixed a real gap in `@infinitetoken/jest-config`'s `knownSubpathMocks`:** it stubbed `@rific/feedback-press/audio`'s `useAudioPool` but not `useGatedAudioPool` — a real risk for this app specifically, since `hooks/useGameSound.ts` re-exports `useGatedAudioPool` directly, and any future test rendering a component that calls it would have hit real `expo-audio`/native audio APIs during a Jest run instead of the intended inert stub. Fixed by adding the same inert-hook stub for it. Now on `@infinitetoken/jest-config@0.3.1`.

**`@tastic/hud@0.9.0` closed the `PlayerSetupPanel` CPU-difficulty alignment gap this app's own earlier migration agent found blocked (no override prop existed at all for the panel's internal `LabeledDropdown`) — `loadout.tsx`'s `p2Panel` now wires the new `cpuDifficultyAlignOverride` prop via `useZoneClampedAlign(p2Host.openId === getCpuDifficultyPopoverId('p2'), LABELED_DROPDOWN_POPOVER_WIDTH, getLabeledDropdownContentHeight(AI_DIFFICULTY_OPTIONS.length))`.** Confirmed, from the actual render tree (not assumption), that this is a documented no-op for this app: `p2Panel`'s CPU seat only exists in `vsCpu` mode, which always renders through the plain stacked (non-`DualZoneLayout`) branch below — only `gameMode === 'twoPlayer'` gets a real `@tastic/split-screen` zone — so `useZoneBounds()` is null there and `useZoneClampedAlign` falls straight back to `useAutoAlign`'s own plain screen-edge placement, same conclusion LightCycles' own `lobby.tsx` already documented for its identical seat before this prop existed. Wired in anyway, for parity with every other zone-aware popover in the fleet and so it starts clamping for free if `vsCpu` is ever nested inside a zone later. `npm run verify` (259/259 tests) stayed green.

## Fleet-wide drift audit round 3 (2026-09-18)

## Fleet package extraction round 2 (2026-09-18)

A second cross-app extraction pass (following the six-piece pass documented under Tooling above) pulled eight more pieces of duplicated fleet code into shared packages; this app adopted all eight. Packages are yalc-linked ahead of publish, same as every other in-flight package in this app's `package.json`: `@rific/core@0.1.4`, `@rific/auto-paper@0.11.1`, `@tastic/achievements@0.1.2`, `@tastic/core@0.7.0`, `@tastic/hud@0.11.0`, `@tastic/profile@0.6.0`. None of the eight touched files (`navigation.ts`, `_layout.tsx`, `Theme.tsx`, `game.tsx`, `useGameStats.tsx`, `achievements.tsx`, `profiles.tsx`) has dedicated component/screen test coverage in this app today — this app's whole `src/__tests__/` suite is engine/utility-level only (physics, AI, faceoff, stats, etc.) — so `npm run verify` passing is a lint/typecheck/unrelated-suite signal for these changes, not a behavioral one; none of them was independently re-verified live as part of writing this section.

- **`safeBack` moved from `src/utils/navigation.ts`'s own hand-rolled implementation into `@rific/core`.** The file is now a 5-line thin binding: `configureNavigation({ router })` (imports `router` from `expo-router`) followed by `export { safeBack }`. `@rific/core` still has zero hard dependencies of its own — it never imports `expo-router` — so `safeBack`'s actual body (`router.canGoBack() ? router.back() : router.replace(fallbackPath)`) lives behind the package's existing `OptionalModule`/`createModuleConfig` injection convention (the same one `@rific/scanner`/`@rific/resizable-input` already use for their own optional peers): `configureNavigation` hands the package a hand-mirrored 3-method `SafeBackRouter` shape, never the real `expo-router` type. `safeBack` itself kept its exact zero-argument signature specifically so every existing bare-reference call site (`onBack={safeBack}`, `onConfirm={safeBack}`) needed zero edits — a parameterized version would have forced every one of those into a wrapped arrow function.
- **The achievement-unlock seat translation and device-wide-broadcast logic moved into `@tastic/achievements`** as two plain functions, `mapUnlocksBySeat`/`broadcastDeviceUnlocks`. `src/hooks/useGameStats.tsx`'s `recordMatchOutcome` (line 65) now reads `const profiles = mapUnlocksBySeat([1, 2] as Player[], context.profileIds, result.profiles)` in place of the old hand-rolled per-seat loop; `src/app/game.tsx`'s `gameOver`-transition effect (line 458) now reads `const broadcast = broadcastDeviceUnlocks([1, 2] as Player[], result.profiles, result.device)` ahead of `setSeatUnlocks(broadcast)` — the 2026-09-17 fix documented above under "Bug fixes" that first introduced `seatUnlocks`/the broadcast-into-both-seats behavior is unchanged in effect, just no longer hand-rolled. Both are true drop-ins for this app (unlike Pong's single-seat `recordSoloOutcome`, which needs an extra wrapping step since it starts from a bare `profileId` rather than an already seat-keyed map) — `mapUnlocksBySeat` preserves the existing own-profile-unlocks-before-device-unlocks concatenation order that `MatchOverlays`' Game Over card display depends on.
- **Quit-confirmation state moved into `@tastic/hud`'s `useQuitConfirmation`** — and this app is one of the three (with AirHockey and Pong, not Snake/LightCycles) where the hook's real signature is load-bearing, not a mechanical swap. The hook takes a **lazy `() => boolean` getter**, not a plain boolean — a deliberate correction made after the hook's first version (a plain boolean) shipped and broke in exactly this app's shape: `paused` (`src/app/game.tsx` line 167, `settingsOpen || confirmVisible`) has to be computed and handed into `useGameState()` *before* that call returns the `scores` state `hasProgress` needs to read, so a plain-boolean argument built from `scores` would have been a genuine circular render dependency (`confirmVisible -> paused -> useGameState -> scores -> hasProgress -> confirmVisible`). This app's own call site (line 166) is `useQuitConfirmation(() => scores[0] > 0 || scores[1] > 0, safeBack)` — the closure is what breaks the cycle, deferring the read to `requestBack`'s own call time (the hook mirrors it into a ref via an effect internally, never reads the closure directly). `paused = settingsOpen || confirmVisible` replaces the old `confirmBackVisible`-named local; the back-button chip now wires `onBackPress={requestBack}` and `MatchOverlaysProps` (the same-file overlay sub-component this app already threaded these through as props, not read-directly) was renamed field-for-field to `confirmVisible: boolean` / `cancelBack: () => void`, keeping its own `onBackPress` prop name rather than renaming it to `requestBack`. `onConfirm={safeBack}` on the `ConfirmDialog` itself is untouched — that was always `safeBack` directly, unrelated to the hook.
- **The achievements screen's universal scaffolding moved out of `src/app/achievements.tsx`** into two new components. The local `MS_PER_DAY`/`startOfDay`/`unlockedLabel` day-diff formatter, the `ACHIEVEMENT_CATALOG.map(...)` row-building loop, and the `ACTIVITY` `<StatSection>` block are all gone; the screen now renders `<ActivityStatSection stats={statsView} />` and `<AchievementCatalogSection rows={getAchievementCatalogRows(ACHIEVEMENT_CATALOG, stats, statsView, unlockedAchievements, effectiveProfileId)} />` (lines 150-152) instead — `getAchievementCatalogRows` (the pure row-computation function, `@tastic/achievements`) does the scope/evalStats/unlockedAt/progress/tierColor/deviceMarker derivation every app's map loop used to hand-roll; `AchievementCatalogSection` (`@tastic/hud`) is the presentational wrapper that resolves the final locked-vs-unlocked badge color and renders one `AchievementRow` per row. Confirmed from the actual current `@tastic/hud` source (not assumed from an earlier design note): `AchievementCatalogSection.tsx` imports `AchievementCatalogRow` as a real `type`-only import from `@tastic/achievements` — its own in-file comment says this replaced an earlier locally-duplicated copy of that interface, kept only until `@tastic/achievements` actually shipped `catalogRows.ts`. The rest of `achievements.tsx` (`OVERALL`/`GOALS`/`VS CPU`/`TWO PLAYER (LOCAL)`/`BOARDS`/`PLAYER RANKINGS` sections, the `!loaded` `ActivityIndicator` branch) is untouched — none of that was ever in scope for this extraction, since those metrics genuinely differ per app.
- **`src/app/profiles.tsx` is now a thin route around `@tastic/profile`'s new `ProfilesScreen` component** — the container `View`, the theme-derived bg/fg computation, the back-button `IconButton`, and the `commitPendingEdit()`-then-`safeBack()` composition (previously hand-rolled via a `ProfilesManagerHandle` ref in every app's own profiles.tsx) all now live inside `ProfilesScreen` itself. This app is one of the two (with LightCycles, not Snake/AirHockey/Pong) that can't adopt it with a fully unchanged `onCreate`, because its own `createProfile` takes a locally-widened `CreateProfileInput` (`{name,color,tag,controlScheme}`) that `ProfilesScreen`'s `ProfileEditPatch`-shaped `onCreate`/`onSave` props don't carry — `onCreate` composes the extra field itself: `(patch) => createProfile({ ...patch, controlScheme: NEW_PROFILE_CONTROL_SCHEME })`, keeping the existing local `NEW_PROFILE_CONTROL_SCHEME` constant. `onSave`, `onDelete` (still wiring both `deleteProfile(id)` and `removeProfileStats(id)`, per the round-2 drift-audit fix above), `defaultColor={defaultColors[0].value}`, and `onBack={safeBack}` are all otherwise identical to the zero-adaptation case (Snake/AirHockey/Pong).
- **`src/app/_layout.tsx`'s corner-flash fix now goes through `@tastic/core`'s `useThemedRootBackground`.** `AppContent`'s `<Stack screenOptions={useThemedRootBackground(dark, false)} />` (line 73, inside `<GuideHost>` since the how-to-play guide landed) replaces what used to be a module-level `SystemUI.setBackgroundColorAsync('#000000')` call plus a local `useEffect`/inline `screenOptions` object literal — the hook now owns both the module-load-time initial guess and the `dark`-keyed live correction, still pairing `contentStyle.backgroundColor` (screen-level backing) with the OS-level root-window background `SystemUI` controls, which is a separate layer `contentStyle` alone never touched. `gestureEnabled` stays a real parameter of the hook (currently passed `false`), not folded into it — it's a logically separate concern (blocking iOS's native swipe-back from fighting an in-game Pan gesture) than corner-flash prevention, and this app's own call site carries no comment explaining the `false` (unlike Snake's/LightCycles' own documented rationale) even though this app's swipe/drag logic — which lives in `Board.tsx`, not a dedicated `TouchInputLayer.tsx` the way AirHockey/Pong/Snake/LightCycles have — very likely needs the same protection; carried forward unchanged rather than "cleaned up," since removing an undocumented flag on a guess would be the wrong kind of drive-by fix.
- **The nested `SplashGate` "settings" + "profiles" double-wrapper in `_layout.tsx` now goes through `@tastic/core`'s `SettingsAndProfilesGate`.** This app already had the merged single-component `GatedApp({children})` shape (confirmed byte-identical to Pong's own version before this migration), so the change is body-only: `GatedApp` still calls `useGameSettings()`/`useProfiles()` itself (the shared component can't call either app-local hook directly) but now returns `<SettingsAndProfilesGate Gate={SplashGate} settingsLoaded={settingsLoaded} profilesLoaded={profilesLoaded}>{children}</SettingsAndProfilesGate>` instead of two hand-nested `<SplashGate gate='settings'>`/`<SplashGate gate='profiles'>` elements. The settings-outer/profiles-inner nesting order, and the fact that neither gate is passed a custom `fallback` (both still default to `null`), are unchanged. `GatedApp`'s own multi-paragraph doc comment explaining why `GameSettingsProvider`/`ProfilesProvider` themselves stay ungated while only what reads their hooks waits is untouched — that reasoning belongs to this app's own provider tree, not to the shared gate component.
- **`src/components/Theme.tsx`'s `AutoPaperProvider` props now come from `@rific/auto-paper`'s new `useThemeBridgeProps` hook.** The trailing `<AutoPaperProvider initialValue={settings} onChange={onChange} onReady={onReady}>` became `const bridgeProps = useThemeBridgeProps({ initialValue: settings, onChange, onReady }); return <AutoPaperProvider {...bridgeProps}>{children}</AutoPaperProvider>` (lines 50-52) — a pure spread-shape change. The `useSelector(state => state.theme, shallowEqual)`/`useDispatch()`/both `useCallback`s above it are all untouched, on purpose: `RootState`'s type and `markSplashReady`'s identity are both app-local, so the hook only ever repackages three already-resolved values into `AutoPaperProvider`'s own prop names, the same modest scope `@rific/feedback-press`'s existing `useFeedbackBridgeProps` (already adopted by this app, see Tooling above) has. In particular this does **not** make the "marked the gate ready before `AutoPaperProvider` was actually ready" bug class (fixed in this file on 2026-09-17, see "Bug fixes" above) structurally impossible to reintroduce — `onReady` is threaded through unchanged, not recomputed, so a future author could still write a wrong callback ahead of ever calling this hook. This app has no dedicated `Theme.test.tsx` (unlike Snake, whose module-factory mock of `@rific/auto-paper` needed updating to also export `useThemeBridgeProps`), so nothing needed updating here beyond the component itself.

## How-to-play guide (2026-09-24)

A first-run, replayable "how to play" flow, built on `@tastic/hud/guide` (a light-peer subpath of `@tastic/hud`; see that package's own CLAUDE.md, "The guide subpath"), following LightCycles' pilot of the same feature. The code word is `guide` everywhere; never call it "onboarding" (Snake and LightCycles already use that for their 3-2-1-GO countdown).

- **Content:** `src/constants/guideSteps.tsx`, `getGuideSteps({ touch, mode, controls, tipoff, scoreToWin })`, pure and hook-free, three cards built from the LIVE settings so a replay after any loadout change still describes the next match: **Shoot the Puck** (the seats' `controlScheme`: one full sentence when both seats share a scheme or the mode is `vsCpu` (solo is always P1, and the CPU's leftover `controlScheme[2]` is irrelevant), the default Flick being "Swipe fast from anywhere. The puck flies the way you swipe.", or a per-player "the puck flies along/against player N's drag" sentence when two humans picked different schemes; direction is always said as where the puck flies relative to the gesture, via `CONTROL_SCHEME_SIGN`, never the loadout's "toward your shot", which can read as "toward the puck"; desktop drags the mouse, never swipes), **First to N Goals Wins** (`scoreToWin`; take turns shooting into **the other player's goal**, and the puck's ring is the only turn cue; never "the far goal", since P1 scores through the top goal and P2 through the bottom, and on desktop web both sit at one upright monitor, so P2's far goal is their own), and a tip-off card for `tipoffMode`: **Win the Face-Off** by default (tap your own half to get ready, then be first to tap your circle that lights up; desktop names A/D and ←/→), **Flip for the First Shot** for Coin Flip, **Tap, Tap, Swipe** for Triple Tap (touch only; desktop can't pick it, so that combination just gets two cards). The tip-off card replaces LightCycles' "Two Players, One Phone": the unlabeled face-off is the one thing that blocks play until you know it, and it's the only place halves matter here (shots start anywhere), so "your own half" lives there and is true solo too (the solo player is P1, whose face-off zone is the bottom half). **Open for Jay:** that (and Triple Tap's "Tap your own half twice") knowingly departs from `@tastic/hud`'s README convention of saying "your half" only on a two-player card, which was written for LightCycles, where it's false solo. If he wants the convention kept literally, the face-off fallback is "Tap near your two circles to get ready..." (the rings are drawn and pulse during the ready check). Illustrations: the shared `SwipeHint` plus this app's own `GuideShotArt`/`GuideGoalArt`/`GuideFaceoffArt`/`GuideCoinArt`/`GuideTripleTapArt` in `src/components/GuideArt.tsx` (plain Views + paper Icons, seat colors from the theme). `GuideShotArt` reads `CONTROL_SCHEME_SIGN`, so the drawn drag direction can't drift from the engine. All five are game-specific and stay local (checked 2026-09-24 against the fleet's shared-art convergence): `GuideShotArt`'s desktop mouse icon is part of the shot picture (puck plus drag direction), not a copy of `SwipeHint pointer='mouse'`; the face-off's A/D and ←/→ are letters on the rink's own circles, not a `DirectionKeysHint` key-cap cluster; and there's no desktop two-player card, so neither `SeatDevicesHint` nor the fleet's "Two Players, One Keyboard/Computer" wording applies here.
- **Copy rules (Jay, 2026-09-24, from LightCycles' review):** Title Case titles, one-word buttons (the pager's Skip/Back/Next/Ready defaults, no `finishLabel`), bodies of 90 characters or less, no em dashes, no rhetorical questions, no near-homophones in one sentence, and every sentence true for every player who can see it (the guide shows on Home before a mode is picked). No card about One Player vs Two Player: those buttons are right behind the dialog. Off-by-default extras (mid-slide steals, shot preview, board variants) aren't taught. Every claim on a card was checked against the engine/input code; the evidence is in `guideSteps.tsx`'s comments.
- **Wiring:** `src/components/GuideHost.tsx` (Redux "seen" version + `useRotation(settings.lockOrientation)` passed as `rotation`, the same rotation Home hands its Settings dialog, + the steps into `GuideProvider`), mounted in `_layout.tsx`'s `AppContent` around `<Stack />`, inside `GatedApp`/`ToastProvider`/`OrientationProvider`. Home (`index.tsx`) calls `useAutoShowGuide()`, Home only, so it can never fire over a live match or a two-seat loadout. Settings row: `SettingsDialog`'s `showHowToPlay` prop into `BaseSettingsDialog`'s `onShowHowToPlay`; on for Home and the loadout, **deliberately off for `/game`** (settings there pauses a live match).
- **Persistence:** `src/redux/guideSlice.ts` (a `createGuideSlice` binding) mounted as `guide` in `store.ts`; the persistConfig key is `'root'` (the factory's default `persistKey`) with no whitelist. `GUIDE_VERSION` (`src/constants/guide.ts`) is what an existing player is stamped with; a fresh install sees the guide once. Only finish/skip writes; a replay never does. Bump `GUIDE_VERSION` only for a real controls/rules change (everyone sees it again).
  - **Players from the shipped pre-redux build are grandfathered by the migrate.** The last shipped update is ad363aa (otaVersion 5, 2026-08-24); the redux-persist root store only arrived in 2af01a6 (2026-09-14), so no shipped player has one, and the slice alone would take them for a fresh install. `store.ts`'s persistConfig has `migrate: createReturningPlayerMigrate(AsyncStorage, LEGACY_STORAGE_KEYS)` (`@tastic/hud/guide`): no root store but any key that build wrote means a returning player, rehydrated as an existing one and stamped with `GUIDE_VERSION`. An existing root store passes through untouched.
  - **`LEGACY_STORAGE_KEYS`** (`guideSlice.ts`): `boxhockey.settings`, `.appearance`, `.playerColors`, `.vibrate`, `.sound`, read from ad363aa's source as literals (a historical record, so never swap in today's constants). otaVersion 2 to 4 wrote the same five and otaVersion 1 wrote nothing. That build recorded no stats or achievements (`useGameStats` and `boxhockey.stats`/`.achievements` came in 2d44b5f, 2026-09-05), and none of its @rific/@tastic packages wrote storage. `boxhockey.settings` is written the first time a mode is picked on Home, so every shipped player who started a match has it.
  - **Nothing may write a legacy key before PersistGate opens**, or a fresh install would be taken for a returning player. Checked 2026-09-24: today's only writer of one is `GameSettingsProvider` (`boxhockey.settings`), mounted under `Providers`' PersistGate and writing only on a real `setSettings`; nothing writes at module load.
- **Not built yet:** a guided practice round against an easy CPU. `game.tsx` records stats/achievements on every game over, so it would need a no-record guard first.
- **Tested:** `guideSteps.test.tsx` (every settings combination: card count, 90-character bodies, art on every card, Title Case, no em dashes/questions, no "swipe" on desktop and no keys/mouse/click on touch, the win/turn/face-off rules stated, no "far goal" and no vague "shot", per-seat copy, solo getting only P1's scheme, and every card's art rendering without crashing, with `SwipeHint` stubbed since this app's Reanimated mock has no `useReducedMotion`), `guideSlice.test.ts` (this app's binding; `LEGACY_STORAGE_KEYS` non-empty, unique and `boxhockey.`-namespaced; `createReturningPlayerMigrate` over a fake storage holding any one legacy key, fed through the reducer's REHYDRATE, gives `GUIDE_VERSION`, with none gives 0, and an existing root store passes through; and the real `store.ts`, loaded fresh against the in-memory AsyncStorage mock through real redux-persist, grandfathers a player with only `boxhockey.settings` and shows a fresh install the guide, which fails if the persistConfig loses its `migrate`). The pager/dialog/provider/slice behavior is covered in `@tastic/hud`'s own suite. **Not verified live** yet: no simulator or browser check of the cards, the art, the auto-show, the grandfathering on a real device updated from the shipped build, or the Settings replay has been done in this app.
- **hud source:** `./guide` shipped in the published `@tastic/hud@0.13.0` (2026-09-25). The guide was first developed against a `yalc link` of the local hud build. That link was removed on 2026-10-01 (`yalc remove --all`, with `package.json` and `package-lock.json` unchanged), so this app no longer uses yalc for any package: there is no `.yalc/` and no `yalc.lock`. src/
  app/          - expo-router routes
  components/   - UI components (board rendering, controls, dialogs)
